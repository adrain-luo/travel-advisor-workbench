## Strongest candidate: mechanisms and limits

`wechatauto/db.py`: `WeChatDB.__init__` calls `_load_or_extract_keys`. Supplied keys and caches are checked before `extract_keys` falls back to `Config.Cipher` discovery using Windows process-memory reads. With no valid key and no running client, extraction fails. Decrypted databases are written to a work directory; the implementation reads source databases and WAL data. Group messages span shards, with per-shard sender mappings, so a bare `local_id` is not a safe occurrence identity. The key loader also searches other-account caches and contains account-switch behavior: specifying an account alone should not be assumed to isolate all reads. An adaptation must remove that fallback and pin the selected account. No process-memory write was found in this database file. [Database implementation](https://raw.githubusercontent.com/fanyuantaier/wechatauto-replica/main/wechatauto/db.py)

`wechatauto/moment.py`: `MomentDB.get_moments` reads local `SnsTimeLine` rows and accepts an exact username filter. This establishes a possible cached-data route, not complete accessible contact history. `parse_feed` retains post ID, author, time, text and XML media metadata; ordered images are represented, but separate image/video lists can lose a combined mixed-media order. Time/keyword filtering uses a bounded intermediate query and therefore needs careful pagination. `find_local_media` can fall back to dimension/size heuristics, which must not be accepted as proven association. `download_media_detailed` first checks cache, then may fetch an already-recorded media URL through HTTP. That is media retrieval, not history backfill. Preserve every expected media occurrence and its failure status. [Moments implementation](https://raw.githubusercontent.com/fanyuantaier/wechatauto-replica/main/wechatauto/moment.py)

`wechatauto/media.py`: `MediaDownloader` reads cached images, voice, video and files. Image decoding may require a separate key obtained from configuration or process memory. `download_image_original` can invoke foreground UI to trigger a missing original, so that route is outside the present no-UI strategy. `download_file` uses resource metadata but can resolve the final cached file by basename; duplicate filenames require stronger verification before attaching bytes to a message. Cached image tier, original availability and decoding success remain distinct. [Media implementation](https://raw.githubusercontent.com/fanyuantaier/wechatauto-replica/main/wechatauto/media.py)

The package also offers sending and UI automation, including memory modification for accessibility. Its package initializer eagerly imports UI modules. A database reader's read-only intent is not evidence that the whole package is harmless to invoke; do not activate its general client or diagnostic entry points as a shortcut. [Package imports](https://raw.githubusercontent.com/fanyuantaier/wechatauto-replica/main/wechatauto/__init__.py), [project description](https://github.com/fanyuantaier/wechatauto-replica)

## Chat-only reference

WeChatMsg-4x's `wx4/key.py` reads process memory and attempts debug privilege; the same file also contains authentication-related key-info diagnostics, which are unnecessary for a narrowly scoped reader. `wx4/reader.py` maps sessions, contacts, group senders and message shards. `wx4/decrypt.py` copies DB/WAL/SHM files and checks decrypted output. `wx4/media.py` handles cached media, but V2 image decoding needs a separate key; an opaque DAT export is not a usable original image. No selected-contact Moments exporter or uncached-history backfill was established. [Key code](https://raw.githubusercontent.com/chenanhan230-del/WeChatMsg-4x/main/wx4/key.py), [reader](https://raw.githubusercontent.com/chenanhan230-del/WeChatMsg-4x/main/wx4/reader.py), [snapshot/decryption](https://raw.githubusercontent.com/chenanhan230-del/WeChatMsg-4x/main/wx4/decrypt.py), [media](https://raw.githubusercontent.com/chenanhan230-del/WeChatMsg-4x/main/wx4/media.py)

## Historical scope decision — subsequently granted

The [implementation brief](../travel-assistant-codex-master-prompt-en.md) explicitly prohibits silently making encrypted-database key extraction a dependency. Activating the strongest candidate without user-provided valid keys would introduce exactly that dependency. The concrete decision is whether to authorize an isolated, read-only key-retrieval experiment against the explicitly selected, authenticated local account, followed by decryption of copies of its required databases. Process writes, injection, authentication-store inspection, private-protocol emulation, other-account searches, installation changes and UI fallback are outside that proposed experiment.

At the time of this review, that decision and subsequent exact-version validation were still outstanding. Even successful local database reading would establish only the recovered cache interval; missing older history and unavailable media must remain visible gaps. User uploads remain supported independently and do not count as scanner acceptance.
